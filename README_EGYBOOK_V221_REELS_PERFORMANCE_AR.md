# EgyBook V221 — المرحلة الثانية: تسريع دخول Reels وتقليل انتظار أول فيديو

## نطاق الإصلاح

هذه المرحلة تعالج انتظار جلب بيانات قائمة Reels وتجهيز سياق أول فيديو. لم تتغير آلية تشغيل الفيديو أو التنقل بالسحب أو التمرير.

## ما الذي تغير؟

1. **كاش لقائمة Reels على مستوى الجلسة**
   - أضيف الملف المستقل `egybook-reels-source-cache.js`.
   - يحفظ بيانات فهرس Neon العامة فقط، لكل حساب ولكل صفحة نتائج.
   - البيانات الحديثة تُعرض فورًا؛ النسخة الأقدم من 45 ثانية وحتى 5 دقائق تُستخدم مؤقتًا مع تحديث القائمة في الخلفية.
   - لا تُخزّن مفاتيح دخول أو رموز جلسات أو نصوص منشورات Supabase الخاصة أو ملفات الحسابات. وتُستبعد روابط الوسائط التي تحتوي على معاملات token/signature/ticket من الكاش.
   - المنشورات المرتبطة تظل خاضعة لاستعلام Supabase الحالي وRLS عند كل تجهيز للقائمة؛ لا يعتمد العرض على نسخة cached من بيانات المنشور.
   - التخزين محدود إلى 3 صفحات لكل حساب، مع التحقق من الروابط والحقول قبل قبولها.

2. **عدم انتظار ملفات الحسابات لفتح أول فيديو**
   - استعلام المنشورات المرتبطة واستعلام ملفات أصحاب الفيديوهات يبدأان بالتوازي.
   - تُنشأ عناصر قائمة الفيديوهات بعد اجتياز فحص Supabase RLS، باستخدام بيانات الملف الشخصي الموجودة بالكاش إن توفرت.
   - استعلام أسماء وصور الحسابات غير الموجودة في الكاش يستمر في الخلفية، ثم يحدّث بطاقة الفيديو عند وصوله.
   - هذا يقلل خطوة انتظار إضافية قبل فتح المشغل، دون تغيير مشغل الفيديو نفسه.

3. **تقليل حمل استعلام Neon لقائمة الفيديوهات**
   - أزيلت استعلامات COUNT الفرعية الثلاثة (الإعجابات والتعليقات والمشاركات) من طلب قائمة `/reels`؛ لم تكن واجهة جلب القائمة تستخدم هذه القيم.
   - أُلغي استدعاء Supabase Auth الزائد قبل طلب GET العام `/reels` فقط؛ بقية مسارات Worker بقيت على التحقق السابق.
   - لم يعد المتصفح ينتظر قراءة جلسة Supabase للحصول على Bearer token عند طلب فهرس الريلز العام.
   - بقيت الأعداد الرسمية متاحة من `/reels/:id`، وهو المسار الذي يستخدمه `reels-stats.js` عند تفعيل الريل.
   - لا يتطلب هذا التغيير SQL migration.

4. **تحديث إصدار الملفات الثابتة**
   - تم تسجيل وحدة الكاش الجديدة في `index.html` وService Worker، مع تغيير أرقام الإصدارات لتجنب تشغيل نسخة قديمة من JavaScript.
   - لم يتم تغيير سياسة Service Worker الخاصة بعدم تخزين استجابات API أو ملفات الفيديو.

## ملفات النشر

- `index.html`
- `script.js`
- `egybook-reels-source-cache.js` (ملف جديد)
- `service-worker.js`
- `cloudflare/egybook-reels-api/worker.js`

انشر Worker أولًا من ملف `cloudflare/egybook-reels-api/worker.js` ثم ارفع محتويات `egybook_work` إلى استضافة الموقع. لا يوجد ملف SQL جديد لهذه المرحلة، ولا يلزم تغيير Secrets أو إعدادات Supabase أو Neon.

## ما لم يتم تغييره عمدًا

لم يتم تعديل الملفات التالية أو ملفات CSS المقابلة لها:

- `video-player.js` و`video-player.css`
- `swipe-navigation.js` و`swipe-navigation.css`
- `infinite-scroll.js` و`infinite-scroll.css`
- `egybook-reels-experience.js` و`egybook-reels-experience.css`
- `evp-interaction-fix.js`
- `evp-caption-layout.js`
- `egybook-video-buffer-manager.js`
- `egybook-video-adaptation.js`
- `egybook-playback-stability-monitor.js`
- `video-transcode-engine.js`

كما لم يتم تعديل `openEgyBookVideo` أو أحداث `touch` / `pointer` / `scroll` أو منطق الانتقال بين الفيديوهات داخل مشغل الفيديو.

## حدود الإصلاح والاختبار

هذا الإصدار يقلل زمن انتظار بيانات الفهرس قبل فتح أول فيديو ويخفف استعلام Neon الخاص بالقائمة. لا يغيّر فك ترميز ملف الفيديو أو طلبات Range أو عرض أول إطار داخل المشغل، لأنها ضمن المشغل الذي أبقيناه دون تعديل عمدًا. إذا استمرت شاشة سوداء بعد فتح المشغل رغم ظهور الواجهة بسرعة، فيلزم فصل تشخيص زمن جلب بيانات القائمة عن زمن استجابة ملف الفيديو/أول إطار، دون تعديل السحب.

تم تنفيذ فحوص محلية لصياغة JavaScript، واختبارات وحدة لكاش الجلسة وعزل الحسابات وانتهاء الصلاحية، وفحص أن العدادات ما زالت موجودة في مسار `/reels/:id`، ومقارنة بصمات ملفات المشغل والسحب والتمرير قبل/بعد. لم يتم الاتصال بقواعد Neon أو Worker المنشور من بيئة البناء؛ لذلك يلزم اختبار فعلي بعد النشر.
