# EgyBook V229.1 — Navigation & Shared Media Stability

## النسخة الأساسية
تم البناء على ملف `EgyBook_V229_Persistent_Navigation_State_Smooth_Transitions.zip` الذي كان أحدث ملف مشروع متاح في هذه المهمة. لم يتم الرجوع إلى V228 أو نسخة أقدم.

## سبب الإصدار
أظهر اختبار المستخدم بعد نشر V229 مشكلتين:
1. الرجوع إلى الرئيسية أو الملف الشخصي كان يعيد الصفحة إلى أعلى بدل استكمال موضع التمرير.
2. معاينات الفيديو الموجودة في الرئيسية والملف الشخصي كانت تُنشأ كعنصري فيديو منفصلين، ما قد يعيد دورة التهيئة/التحميل عند الانتقال بينهما.

## التعديلات المنفذة

### 1) إصلاح استعادة موضع الصفحات
- التقاط موضع الصفحة المغادرة في مرحلة `pointerdown` و`click` قبل وصول الحدث إلى معالجات التنقل التي قد تخفي الصفحة أو تنفذ `scrollTo(0)`.
- حفظ احتياطي عند حدث `egybook:primarypagechange` فقط عندما تكون الصفحة المغادرة ما زالت ظاهرة؛ لا يُحفظ الصفر بعد إخفاء الصفحة.
- تعديل محدود في `routeToProfile()` يمنع أمر `scrollTo(0)` القديم من الكتابة فوق موضع ملف شخصي محفوظ؛ عند عدم وجود موضع محفوظ يظل السلوك القديم (البدء من أعلى الملف) كما هو.
- تمييز موضع كل ملف شخصي بمفتاح مستقل يتضمن اسم المستخدم.
- الانتظار حتى يصبح سطح الصفحة المستقبلة ظاهرًا ويصبح ارتفاع المستند كافيًا للوصول إلى الموضع المحفوظ، بدل الاستعادة المبكرة إلى الصفر.
- دعم استعادة آخر موضع محفوظ عند إعادة تحميل نفس علامة تبويب المتصفح.
- إبقاء `Back/Forward` تحت مسؤولية مستعيد سجل التصفح الموجود أصلًا داخل `script.js`، دون تركيب مستعيد منافس.
- استثناء Reels من استعادة تمرير المستند؛ يظل محرك Keep-Alive الحالي مسؤولًا عن جلسة الريلز.

### 2) مشاركة معاينة الفيديو بين Home وProfile
- إضافة وحدة مستقلة `egybook-shared-feed-media.js`.
- عند وجود المنشور نفسه في `#postsList` و`#profilePostsList` وبنفس رابط الوسيط المطابق، تحتفظ الوحدة بعنصر `<video>` أصلي واحد وتنقله بين موضعي المنشور حسب الصفحة النشطة.
- لا تنشئ الوحدة طلب `fetch` للوسائط، ولا تضيف كاشًا للوسائط، ولا تنقل الفيديو إلى Service Worker.
- لا يُعاد استدعاء `load()` على عنصر الفيديو المحتفَظ به؛ يتم تحرير عنصر المعاينة المكرر فقط.
- عند إعادة إنشاء قائمة منشورات الملف الشخصي، تعيد الوحدة العنصر المحتفَظ به إلى البطاقة الباقية ثم تعيد ربطه بالبطاقة الجديدة عند تطابق المنشور والرابط.
- تستمر الوحدة في تسجيل عنصر الفيديو المحتفَظ به مع `EgyBookSmartFeed` الحالي، ولا تستبدل نظام تشغيل الفيديو.
- المشاركة محدودة بالمعاينات الموجودة داخل Home وProfile وبمعرّف المنشور نفسه ورابط وسيط مطابق تمامًا. الروابط المختلفة لا تُدمج لتجنب خلط صلاحيات أو روابط تشغيل مختلفة.

### 3) سلاسة الانتقال
- إضافة انتقال ظهور خفيف بالشفافية لمدة 190ms للصفحة الرئيسية والملف الشخصي والرسائل والإشعارات.
- احترام `prefers-reduced-motion`.
- عدم إضافة `transform` إلى جذور هذه الصفحات لتجنب إنشاء containing block جديد قد يؤثر على العناصر الثابتة.

### 4) الكاش
- تحديث رقم نسخة Service Worker.
- تحديث مراجع CSS ووحدة التنقل الجديدة في HTML وقائمة الملفات الأساسية.
- تظل سياسة Service Worker كما هي: لا يتم تخزين الفيديوهات أو ملفات الوسائط أو بيانات المستخدم الخاصة في الكاش.

## الاختبارات
- `node --check` لملف التنقل، وملف مشاركة الوسائط، وService Worker، وملف الاختبار.
- `node tests/navigation-state-v229.test.cjs` — سبعة اختبارات ناجحة.
- فحص Static Site: التحقق من 27 ملف HTML و22 مرجعًا لإصدارات Supabase SDK المثبتة.
- تشغيل صفحة الاختبار `tests/v2291-browser-checks.html` داخل Chromium headless على إطار محاكاة هاتف 390×844 مع DPR=2، وإطار سطح مكتب 1365×768 مع DPR=1، باستخدام DOM تجريبي دون قاعدة بيانات أو ملف فيديو حقيقي.
- أُعيد تشغيل الاختبارات الخمسة على كلا الإطارين، ونجحت النتائج في كليهما. فُحص حفظ Home وProfile واستعادة موضعيهما بعد الرسائل، وحصر المنشور المشترك في عنصر فيديو واحد، والحفاظ على هوية عنصر الفيديو عند نقله وإعادة إنشاء قائمة Profile. لم تظهر أخطاء JavaScript في صفحة الاختبار.

## حدود الاختبار
لم يتم اختبار موقع GitHub Pages المنشور بحساب حقيقي، أو تدفق فيديو فعلي، أو خادم Supabase/Neon/R2/Hovod. ولم يتم إجراء اختبار على هاتف فعلي أو Safari أو Android WebView. اختبار Chromium كان اختبار DOM تجريبيًا على إطار محاكاة هاتف وإطار سطح مكتب، وليس اختبارًا على جهاز حقيقي.
