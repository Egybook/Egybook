# EgyBook V240 — Media Pipeline Diagnostics

## الأساس والنطاق
- النسخة الأساسية: `EgyBook_V239_Unified_Reels_Playback.zip` التي رفعها المستخدم.
- دستور التطوير: `EgyBook_Development_Constitution_Complete_v2.docx`.
- الغرض: بدء خطة محرك الوسائط المستوحاة من المبادئ الهندسية المنشورة عن Meta بقياس مسار الوسائط الفعلي قبل تغيير ملكية عناصر الفيديو أو فك الترميز.
- هذا الإصدار مرحلة تشخيصية فقط؛ لا يدّعي تنفيذ Media3 أو نسخ البنية الداخلية لـFacebook.

## ما كشفته مراجعة V239
1. معاينة السحب المجاورة هي عنصر `HTMLVideoElement` منفصل ومكتوم، محفوظ داخل Warm Cache صغير.
2. عند اكتمال السحب، تستمر المعاينة كغطاء بصري وتواصل التشغيل، بينما يفتح المشغل الأساسي `#egybookVideoPlayer` مصدر الفيديو نفسه عبر `src` ويزامن موضعه مع ساعة المعاينة.
3. لذلك يوجد عنصر معاينة وعنصر مشغل أساسي منفصلان خلال فترة التسليم. قد يزيد ذلك ضغط الشبكة وفك الترميز، لكن لا يمكن من الكود وحده إثبات أن المتصفح ينقل بايتات الفيديو مرتين؛ قد يعيد استخدام HTTP cache أو يتصرف وفق Range/cache headers.
4. `reusedSwipePreview: true` يعني أن معاينة السحب استُخدمت كمرجع توقيت/موضع أثناء التسليم؛ لا يعني أن المشغل الأساسي تبنّى نفس عنصر الفيديو أو Decoder.
5. `originConnected: false` في فتح Reels عبر Queue متوقع؛ دالة الانتقال تمرر `originVideo` بقيمة `null`، بينما عنصر المعاينة يمرر منفصلًا عبر `transitionCover`. لا يُعامل هذا الحقل وحده كخطأ.
6. V239 يجهّز مستوى صوت المشغل الوارد عند الصفر مؤقتًا ثم يفعّل الصوت بعد نجاح `play()`. قياسات V239 سجلت اكتمال التدرج بعد نجاح التشغيل بفترة قصيرة، لكنها لا تقيس وحدها جاهزية مسار الصوت الداخلي أو توقيت أول عينة صوتية مسموعة.

## التغييرات في V240
### 1. توسيع المراقب السلبي إلى V55
- الإبقاء على قياسات المشغل الأساسي السابقة: زمن أول إطار، بدء التشغيل، الانتظار، التوقف بسبب الشبكة، وأخطاء الوسيط.
- إضافة أحداث تشخيصية للمشغل الأساسي مثل `loadedmetadata`, `canplay`, `progress`, `seeking`, `seeked`, `suspend`.
- إضافة مراقبة اختيارية لمعاينات Reels/Warm Cache عند فتح الصفحة مع `?videoDebug=1`.
- قياس `readyState`, `networkState`, playhead, الأبعاد، الكتم ومستوى الصوت، playback rate، buffered ranges، والوقت المتاح داخل buffer.
- تسجيل Resource Timing إذا أتاح المتصفح المعلومات، مع مؤشرات الشبكة التي يوفرها `navigator.connection` عند توفرها.
- استخدام بصمة قصيرة لمصدر الوسيط بدل تضمين عنوان URL كامل في سجلات القياس الجديدة.
- إضافة `watchMedia`, `unwatchMedia`, `snapshotMedia`, و`recordMedia` للمراقبة والتشخيص فقط.

### 2. نقاط ارتباط داخل Reels
- تسجيل لحظة إنشاء عنصر Warm Cache وأولوية `next/previous`.
- تسجيل لحظة ربط المعاينة بعملية السحب وطلب تثبيت الانتقال.
- تسجيل لقطة مقارنة بين معاينة السحب والمشغل الأساسي قبل فتح المصدر الوارد، تشمل تطابق المصدر وحالة كل عنصر.
- لا تتغير قرارات التحميل أو توقيت السحب أو `play()` أو `pause()` أو `src` بسبب هذه القياسات.

### 3. تقرير الفيديو
- عند فتح الموقع مع `?videoDebug=1`، يلتقط زر «تقرير الفيديو» أحداث مسار الوسائط.
- يضم التقرير آخر 120 سجلًا، ويحتفظ بالتخزين المحلي السابق دون مسحه.
- Resource Timing قد يكون ناقصًا لمصادر Cross-Origin التي لا تسمح بسياسة Timing-Allow-Origin؛ الصفر أو عدم توفر البيانات لا يثبت أن الملف لم يُحمّل أو أنه من الكاش.

## ما لم يتغير
- لم تتغير خوارزمية السحب الرأسي أو حساسيته أو حركة Push Transition.
- لم يتغير حد Warm Cache أو سياسة `preload` أو ترتيب أولوية الفيديو التالي والسابق.
- لم تتغير ملكية الصوت أو توقيت V239 أو مستويات fade-out/fade-in.
- لم يتغير `Unified Video Player`, `Keep-Alive`, `Persistent Navigation State`, `Reels Return Recovery`, `Direct Preview Handoff`, أو تجديد روابط Hovod.
- لم تتغير واجهة المستخدم أو CSS أو الهيدر العلوي أو السفلي أو شريط تفاعلات Reels.
- لا تغييرات في SQL أو RLS أو Supabase أو Neon أو R2 أو Cloudflare Worker أو Hovod.
- لم تُحذف ملفات أو وظائف أو إعدادات أو بيانات.

| V240 | قياس خط التحميل والمعاينة والمشغل الأساسي والصوت قبل التغيير | منفذة محليًا؛ تحتاج تقرير هاتف |
| V241 | تصميم تسليم موارد المعاينة للمشغل وتقليل ازدواج decoder/الطلبات دون كسر هوية المشغل الموحد | تبدأ بعد تحليل تقرير V240 وتحديد خيار آمن |

| V243 | إدارة ميزانية الموارد للمعاينات والـDecoder بناءً على إشارات الجهاز المتاحة | لاحقة لـV242 |
| V244 | مزامنة جاهزية الصوت مع الفيديو ومنع الصمت أو التداخل عند الانتقال | لاحقة لقياسات V240 وV241 |
| V245 | دراسة Loudness normalization ومسارات الترميز المدعومة قبل تنفيذ أي تطبيع صوتي | لا يبدأ دون إثبات توافق المصدر والمنصات |

لا يُفترض أن `xHE-AAC Loudness Management` يمكن نسخه إلى HTMLMediaElement بمجرد تغيير مستوى الصوت؛ ذلك يحتاج دراسة مسار الترميز/البيانات الوصفية والتوافق الفعلي للمنصات. لا ينفذ V240 أي تحويل صوتي.

## الاختبار المطلوب على الهاتف
1. انشر ملفات V240 للواجهة وService Worker فقط وفق طريقة النشر المعتادة؛ لا تنشر Worker ولا تنفذ SQL.
2. افتح الرابط مع `?videoDebug=1`، ثم أدخل Reels.
3. نفّذ 10–15 انتقالًا متتابعًا بسرعة عادية، ثم 5 انتقالات أسرع، وانتظر بعد بعض الانتقالات عدة ثوانٍ.
4. جرّب ريلًا بصوت، وآخر بصوت مختلف، وآخر صامتًا، مع الكتم والتشغيل.
5. صدّر «تقرير الفيديو» بعد ظهور علامة التحميل أو تأخر الصوت.
6. كرر مرة على نفس الشبكة ومرة على شبكة أسرع إن توفرت، دون تغيير الجهاز أو مسح بيانات الموقع.

## قيود الإثبات
- اختبارات V240 محلية ومحاكاة Node؛ لا يوجد اختبار فعلي على Android/Chrome أو WebView أو Safari من جهة التطوير.
- Resource Timing لا يضمن قياس حجم النقل في كل Cross-Origin.
- قياس `playing` لا يساوي قياس أول عينة صوت مسموعة، ولا توجد واجهة موحدة موثوقة عبر كل المتصفحات لقراءة أول عينة صوتية.
- لم تُجرَ تغييرات سلوكية لتحسين سرعة التحميل أو توقيت الصوت بعد؛ المرحلة الحالية تجمع بيانات لاتخاذ قرار آمن.
